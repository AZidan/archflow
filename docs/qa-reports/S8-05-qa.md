`/archflow:status <secret> <path>`, `/archflow-groom S1 <secret>`, `$archflow-status <secret>`, the Gemini

Result: 8 events per host, and **no secret, path fragment or argument appeared in any payload**. Hand-edited

I tested `DO_NOT_TRACK`, `CI` and `ARCHFLOW_TELEMETRY_DISABLED`, each with 13 values, on session start

## Issues

### I-1 (blocking): the notice is discarded on Copilot but is still marked shown, for the whole machine

`plugin/hooks/telemetry.mjs:115-118` `showNoticeOnce()` writes `NOTICE` as plain text to stdout and then
calls `recordNoticeShown()`. On Copilot the SessionStart hook is wired as a plain command
(`scripts/build-adapters.mjs:946`, generated `adapters/copilot/.github/hooks/archflow.json`). GitHub's
Copilot hooks reference (docs.github.com/en/copilot/reference/hooks-configuration) says the hook's stdout
is "parsed with a single `JSON.parse` call", and "if the leftover output ... fails to parse as JSON, the
hook is treated as having produced no output". It also says "Only `additionalContext` is consumed for
`sessionStart`", and that this applies to both camelCase and PascalCase event names.

- **Expected:** the first Copilot session shows the notice to the user or the model, then marks it shown.
- **Actual:** the notice text is dropped. `noticeShownAt` is still written to `~/.archflow/config.json`,
  so the notice is never shown again on any host on that machine. Telemetry is on by default, so a
  Copilot-first user is never told. The same applies when Copilot loads the Claude plugin directly,
  because `plugin/hooks/hooks.json` is also plain stdout.
- **Repro (local):** run `node adapters/copilot/.github/archflow/hooks/telemetry.mjs` with a fresh
  config. Stdout is the plain-text notice, not JSON, and `config.json` gains `noticeShownAt`.
- **Caveat:** this finding comes from the vendor documentation. I did not run a live Copilot CLI session.
  The Copilot `cat .archflow/instructions.md` SessionStart entry relies on the same plain-stdout
  assumption, which is outside this story. Before fixing, confirm on a live Copilot CLI. The likely fix
  is to emit `{"additionalContext": ...}` on Copilot, the way the Cursor bridge wraps output in
  `additional_context`.

Other hosts were checked against their documentation:
- Gemini treats non-JSON stdout as a `systemMessage`, so the notice is shown.
- The Cursor bridge wraps the notice in `additional_context`.
- OpenCode pushes it into `output.system`.
- Codex and Claude Code inject plain SessionStart stdout as context.

### I-2 (minor): SECURITY.md says "The first run prints a one-time notice", but a command event can be sent first

`SECURITY.md:97`. Prompt-submit hooks (Codex, Copilot, Cursor, Gemini) intentionally print nothing
(`plugin/hooks/telemetry.mjs:152-157`). If a prompt hook fires before any session-start hook has printed
the notice, one `command_run` is sent and the notice waits for the next session start. I confirmed this
on all 7 hook entries. A `command_run` went to the sink while `config.json` held only `distinctId`, and
the notice appeared at the following session start.

The case is uncommon, because session start normally runs first in a session. It does happen when the
session-start hook did not run, or when its output was discarded (see I-1). On Claude Code, the notice
also reaches the model, which is asked to relay it, rather than being printed directly to the user.
The sentence needs a qualifier, for example: "The first session start prints a one-time notice (on
hosts that detect commands from the prompt, a command event can precede it if no session start has run
yet)".

## Other checks (no issue filed)

- **The `ARCHFLOW_TELEMETRY_SINK` escape hatch cannot exfiltrate data.** It is read after the `isEnabled()`
  and allow-list checks. It only appends the already-filtered payload to a local file with
  `appendFileSync`, and it returns before `spawn`, so no network sender starts. The suite's
  `test_capture_never_spawns_the_sender_when_the_sink_is_set` confirms this. Anyone who can set the
  variable already controls the process environment. It is documented only as a "Test seam" in the
  code comment (`plugin/lib/telemetry.mjs:232`), not in SECURITY.md, which is acceptable for a test-only
  variable. A side effect: setting it acts as an opt-out.
- **OpenCode:** `archflow-<unknown>` is not reported, because `commandFromName` requires a name from
  `lib/commands.json`. I confirmed this at the hook level. The TypeScript plugin itself was not run,
  because there is no OpenCode runtime here.
- **`cli_install`:** `source` covers every origin string in `scripts/archflow.mjs`, because tags are
  validated as `^\d+\.\d+\.\d+$`, and `installed_hosts` covers the CLI host keys.
- **Not in SECURITY.md:** `$process_person_profile: false` is a PostHog processing flag sent in every
  payload. It is not user data.
- **Leftover `/archflow:status/<suffix>`:** this is counted as `archflow:status`. The lookahead allows `/`,
  but only the command name is sent.
- **Stale subtasks:** the release file still has "Verify the default is on (opt-out) on every host" and
  "Tests for event allow-list" as `completed: false`, although `tests/test_telemetry.py` covers both.
  Updating them is the implementer's job.
- **Out of scope (S8-06):** `/archflow:telemetry` documentation and `--status` wording.
