### Ruling: Gemini `extensions update` path, recorded as I-6 (blocking)

`installGeminiFrom` (`scripts/archflow.mjs:533-549`) handles "already installed" by running `gemini extensions update archflow`. Gemini CLI records an extension's install source in its install metadata, and for a local-path install `update` re-copies from that recorded path. It does not use the newly staged folder. The installer itself says so in its comment at `scripts/archflow.mjs:527`. So, for every existing Gemini CLI user upgrading:
- **From 2.4.0:** 2.4.0 ran `gemini extensions install <package or release cache>/adapters/gemini` (`git show 2.4.0:scripts/archflow.mjs`, `installGemini`). That source has no `server/` or `dist/`, because the bundle is staged separately by `installStudio`. Depending on what sits at the path now, the update reinstalls the 2.4.0 extension (no studio command at all), reinstalls the current adapter without the bundle, or reports "up to date" and changes nothing. In none of these cases does the bundle reach `~/.gemini/extensions/archflow`.
- **From 2.5.0 onward:** the recorded source is `~/.cache/archflow/gemini-extension/<old version>/archflow`, which the update path deliberately keeps. The update reinstalls the old version.
- The installer still prints `copy ~/.gemini/extensions/archflow/server/server.mjs, .../dist/ (Archflow Studio)` on this path (seen in the fake-gemini run), which is false. `/archflow:studio` then reports the bundle missing, and its remedy, `npx archflow@latest install`, goes through the same update path. That is the I-3 loop again, on Gemini.

This makes the criterion "npx archflow install copies the bundle for each host" false for a realistic case: any Gemini user who installed through the Gemini CLI before. This was assessed from the code and Gemini's documented install-metadata behaviour. The local Gemini CLI (0.1.7) predates `extensions install/update`, and nothing was installed to check it. Direction for the fix (not applied): on "already installed", run `gemini extensions uninstall archflow` and then install from the staged path, or fall through to the direct copy. Then pruning can run on every path.

### Cancel with Ctrl-C at a Gemini prompt: FAIL (I-8)
```
$ expect ctrlc.exp node scripts/archflow.mjs install --host gemini ...   # sends ^C at the first [y/N]
Do you want to trust this folder and continue with the installation? [y/N]:
(the installer prints nothing more: no fail line, no "Not fully installed")
$ ls -a $H/.gemini           → archflow-extension.previous  extensions ...
$ ls -a $H/.gemini/extensions → extension-enablement.json   (no archflow)
$ gemini extensions list      → No extensions installed.
```
In a terminal, Ctrl-C sends SIGINT to the whole foreground process group. That group includes the
node installer blocked in `spawnSync(..., { stdio: "inherit" })`, so node exits before the
restore code runs. The user's working extension sits in `~/.gemini/archflow-extension.previous`,
which Gemini does not load, and nothing tells them so. A later re-run sees no extension
(`had=false`) and does a fresh install. When that is accepted it prints `Installed.`, but the
orphaned `.previous` (4.8 MB here) is never removed, because it is only cleaned when `had` is
true. When that re-run is declined, the user still has no extension. Gemini's own prompts invite a
cancel, and the code's own comment lists "cancelled" as an expected outcome, so this is a
realistic case that does damage. Direction (not applied): ignore SIGINT in the parent while the
child runs (`process.on("SIGINT", ...)` around the spawn, or install a handler that restores
`prev` before exiting), and have a later run restore or clean up a leftover `.previous` when
there is no `extensions/archflow`.

### Ruling: exit code 1 when the Gemini install is skipped (no terminal) or declined
Not an issue. The install did not complete, so a non-zero exit is the honest result, and the
CHANGELOG states it ("With no terminal (CI, piped) it prints the command to run instead and exits
1"). It affects only jobs that run the installer with `gemini` on PATH. The project hosts (cursor,
codex, copilot, opencode, generic) are unaffected, and with no `gemini` on PATH the installer still
copies straight into `~/.gemini/extensions`. The trade-off is that a CI job has no supported way to
install the Gemini extension through the CLI, since there is no opt-in flag for that. Gemini's
trust prompts make this the user's decision, so that is acceptable. A CI job that installs several
hosts at once should run `--host gemini` separately.
