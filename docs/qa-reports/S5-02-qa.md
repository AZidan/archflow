## Issues

### I-1 (blocking): an aborted run with parked stories is a dead end

- **Location:** plugin/commands/autopilot.md:248-251 (the `Next:` rule), :314 (resume refuses aborted runs), :319 (`abort` prints Step 4), and plugin/commands/status.md:34.
- **Repro (by reading the spec):**
  1. A run parks S1-02, then the user runs `/archflow:autopilot abort`.
  2. `abort` sets `status: aborted` and prints Step 4. Step 4's rule is "With parked stories it is the line above", so the report says `Next: /archflow:autopilot resume — asks the parked questions...`.
  3. The user runs it. Resume rule 3 says "An `aborted` run is never resumed", so it prints `Nothing to resume.`
  4. `/archflow:status` case 3 still tells the user to run `/archflow:autopilot resume` for S1-02, unconditionally.
- **Expected:** the report and status name a command that actually brings S1-02 back. That is the exact contract this story set for finished runs.
- **Actual:** S1-02 stays `parked` and no command leads anywhere. Step 1 excludes `parked` from the default queue, and nothing documents how an explicit-id run clears a `parked` block. Abort is documented as bookkeeping that leaves state intact, so it is the common way to end up here.
- **Fix options (for the implementation agent to choose):**
  - Let rule 2 also start a follow-on run over an *aborted* run's still-parked stories. The aborted ledger stays aborted, so "aborted runs stay aborted" still holds for the run itself.
  - Or give abort's `Next:` line, and status case 3, a working alternative. It would need its own documented exit from `parked`.
- **Test:** `tests/test_autopilot_resume_qa.py::test_abort_report_next_line_names_a_command_that_works_for_an_aborted_run` (strict xfail).

### I-2 (minor): follow-on resume does not check the release

- **Location:** plugin/commands/autopilot.md:296-308.
- **Problem:** rule 2 checks that a story is "still `status: parked` in the release file" but never says which file, and never checks that the finished ledger's `release` is still `active_release`.
- **Why it matters:** a release may ship with a non-blocking parked story (`blocks_release: false`) and be archived. Resume would then edit an archived or other release file, which the hard constraints forbid ("Touch ... any other release file").
- **Also:** rule 2 does not restate that the Prerequisites (clean tree, phase ≥ 3) apply before writing the new ledger. Rule 1 does not restate them either, but rule 2 writes state.
- **Expected:** skip, or report, parked stories whose release is no longer active.

### I-3 (minor): a stale preflight ledger outranks parked work

- **Location:** plugin/commands/autopilot.md:292.
- **Problem:** rule 1 selects the newest `preflight` or `running` ledger at any age, before rule 2 looks at finished runs. Take a `--plan` ledger that was never started, plus a finished run with parked stories. A user following status case 3 ("answer the parked question via resume") instead starts the old planned queue unattended, and the parked question is not asked.
- **Context:** this precedence existed before the story, but the story now routes every parked story through `resume`.
- **Expected:** state the precedence explicitly in the status advice, or have rule 1 also gather finished runs' still-parked stories.

### I-4 (minor): landing page keeps the old wording

- **Location:** docs/index.html:680.
- **Problem:** the page still says "Answer, then `/archflow:autopilot resume` picks up where it stopped". That is the two-step phrasing the story removed from README and status. The uncommitted `docs/index-next.html:691` has the same line.
- **Expected:** match README:198. Resume asks the questions itself, and it works after a run finished.

## Other scrutiny (no issue raised)

- **Reaching past a newer finished run with nothing parked to an older one:** sound. Each queue item is cross-checked against the release file, so stories resolved by a later follow-on drop out. When two finished runs both hold parked stories, it takes successive `resume` calls (newest run first), but each call makes progress.
- **Parked story un-parked by hand:** handled by the "still `status: parked`" cross-check and by rule 3's "(or whose parked stories have all been resolved since)".
- **Run branch merged and deleted:** a fallback to `base_branch` is documented. The WIP task branches were cut from the old run branch, and merging them into the new run branch is safe once the old branch is merged into base.
- **Guard hook:** arms only on `running` or `preflight`, so a finished parent never arms it and a follow-on does. Both are tested.
- **Validator:** skips finished and aborted ledgers (validate_archflow.py:300-314).
- **Release schema:** `parked` → `in_progress` is the documented exit, and rule 2 uses it.

### Scrutiny points from the brief

- **run_branch deleted or merged:** the "Some answered" path uses `run_branch` if it exists, else cuts a new branch from `base_branch`. That works when the run was merged into base, because base then carries the ledger and `parked` state. If the run branch was deleted without being merged, the re-read on a fresh branch from base finds nothing parked and drops every answer. Rule 2 then has no stop, which is I-14.
- **Duplicate copies of one ledger (run branch merged into base):** when the current checkout holds the ledger, it wins and branches are not scanned. When it does not, "newest" ties on run-id and the tie-break is undefined. In practice this is harmless, because the "Some answered" path re-reads state on the run branch before writing. No issue raised.
- **active_release:** it is read from the current checkout's `current-phase.yaml`, the same place the Prerequisites read it. Autopilot never changes `active_release` on the run branch, so the two cannot diverge through autopilot. No issue raised.
- **Clean tree vs checkout:** Prerequisites are checked first, so the checkouts in rule 2 run on a clean tree. However, the run's own terminal writes leave the tree dirty, which is I-12.

### New issues

#### I-12 (blocking): terminal ledger writes are never committed, so the documented `resume` HALTs, and the branch scan reads a stale `running`

- **Location:** plugin/commands/autopilot.md:261 (Step 4's closing write), :384 (`abort`), :107 (`--plan` preflight ledger), against :32 (clean-tree prerequisite, applied to resume at :298-300).
- **Steps:** a run finishes or is aborted. Step 4 or `abort` sets `status: finished` or `aborted` in the ledger and stops. Nothing says to commit that write. Step 3 commits the ledger only per story (:150, :164). `--plan` likewise writes a `preflight` ledger and stops without committing it.
- **Actual:** the user follows the report's `Next: /archflow:autopilot resume`. Resume checks Prerequisites first, sees a dirty tree (` M .archflow/autopilot/{run-id}.yaml`, or an untracked preflight ledger), and HALTs. Prerequisites forbid stashing. A user who stashes or discards the change to get unstuck leaves the committed ledger at `running`. The scan added in I-7 then reads `running` through `git show`, and rule 1 continues the run. For an aborted run, that continues its queue.
- **Reproduced:** in a scratch repo, a ledger committed as `running` on `run` and then rewritten to `aborted` uncommitted gives `git status` = ` M .archflow/autopilot/r.yaml`. `git checkout base` is refused ("Your local changes ... would be overwritten"). After `git stash`, `git show run:.archflow/autopilot/r.yaml` returns `status: running`.
- **Expected:** the closing write, `abort`'s write and the `--plan` ledger are each committed when written, the same way Step 3 commits as it goes. Only then is the end-of-run `Next:` line runnable as-is, and the aborted record survives on the branch the scan reads.
- **ACs affected:** "The end-of-run report's 'Next:' line names a command that actually works for a finished run" and "aborted runs stay aborted". The clean-tree check on resume was introduced by this story (fix pass 1). Before that, resume did not check it.
- **Test:** `test_terminal_ledger_writes_are_committed` (strict xfail).

#### I-13 (minor): the branch scan short-circuits on any candidate in the current checkout, so the two-candidate choice can be made on half the picture

- **Location:** plugin/commands/autopilot.md:314 ("If it holds no candidate, scan ... every local branch").
- **Scenario:** run B finishes with S1 parked on `run-B`. The user switches back to base without merging, then runs `--plan`, which writes preflight ledger A on base. Then the user runs `resume` to answer S1.
- **Actual:** the current checkout holds a candidate (preflight A), so other branches are not scanned. Only one candidate is seen, so rule 1 applies and planned run A starts unattended. The "planned run or parked questions?" question is never asked. That regresses I-3. The mirror case: a finished candidate on base plus an interrupted `running` ledger on its run branch means the interrupted run is missed.
- **Expected:** collect both candidate kinds across the current checkout and all local branches, then apply the choice rules. Preferring the current checkout should only break ties between copies of the same ledger.
- **Test:** `test_branch_scan_does_not_stop_at_the_first_checkout_with_a_candidate` (strict xfail).

#### I-14 (minor): rule 2 has no stop when the re-read on the run branch drops every answer

- **Location:** plugin/commands/autopilot.md:362-364.
- **Scenario:** the answers were given against the source branch's state. On the run branch (or on a branch freshly cut from `base_branch` when the run branch is gone), every answered story is no longer `status: parked`.
- **Actual:** "drop from the answers any story no longer parked. Then, on that branch: Write a new ledger ...", so a follow-on ledger with an empty queue is written and committed, and Step 3 and Step 4 run on nothing.
- **Expected:** if nothing is left after the re-read, write no ledger, tell the user which stories were already resolved, and stop. The "nothing answered" branches already do this.
- **Test:** `test_follow_on_stops_when_the_reread_drops_every_answer` (strict xfail).
