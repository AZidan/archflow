An idea becoming a groomed story with acceptance criteria, in the chat panel.

It sets itself up

Point it at a folder and Studio starts onboarding: in its own panel on Claude Code, in your terminal everywhere else. An older project gets a one-button migration to the current schema. Either way you land on a board, not a blank file.

Its chat runs your host, or feeds it

On Claude Code, Studio runs the agent in the panel, and if you opt in it can start from your running session’s history, forked. On every other host it composes the prompt, spelled the way your host expects, and hands it to the terminal session you already have open. Nothing runs behind your back; you see every prompt before it goes.

It runs on your machine

Binds to 127.0.0.1 with an origin allowlist. No hosted service, no account. Your code and your credentials never leave the machine; only anonymous usage events do, and you can turn those off.

Studio runs on every supported coding agent: in its own panel on Claude Code, and through your own terminal session on the rest.

It’s marked beta because features are still landing, and because what you tell us is missing decides which land next. Anonymous usage telemetry is on by default and never includes code, prompts, paths or project names; /archflow:telemetry off or DO_NOT_TRACK=1 turns it off. What is sent.

Hand it the release. Go to sleep.

Autopilot asks you everything it can’t decide alone up front (in one batch), then goes silent and builds story after story. One report in the morning.

/archflow:autopilot

The interview comes first: product behaviour, trade-offs, anything irreversible, each as a question with real options to pick from. Your answers are written to a run ledger before any code moves, so they survive the hours, and the context compactions, that follow.

It asks before, not during

Every blocker it can see in the queued stories gets asked while you’re still awake. Nothing it could have looked up in the API contract or design artifacts becomes a question.

It parks, it never guesses

A new decision at 3am doesn’t stall the night or get answered for you. The story is parked with the open question, its work committed but unmerged, and the run moves on.

It stops short of main

Everything lands on one branch. No merge to main, no pull request, no deploy, nothing that costs money. You review a night’s work and merge it yourself.

/archflow:onboard

Your prototype works. People are using it. What it doesn’t have is a roadmap, an API contract, a test plan, or a defensible answer to what 1.0 means. Onboarding audits what you shipped and reconstructs the plan around it; where it finds working code with no story behind it, it writes the story and marks it delivered.

What this does and doesn’t do: you get the plan, contracts, and quality gates your prototype never had, and Phase 4 agents review code quality, security, and performance. Archflow will not silently rewrite your architecture. You decide what gets refactored; it makes sure you know what needs it.

What’s underneath

One agent per job. Files as handoffs. Phases as guardrails.

Studio is a window onto a process that also runs fine from the terminal. Running on 1,100+ projects, including this one: the .archflow/ directory is in this repo.

17 specialized agents

Each scoped to one domain. A UX designer doesn’t write backend code. An API engineer doesn’t make design decisions. Each loads only what its own job needs, so no cross-contamination of concerns.

File-based handoffs

Agents communicate through artifacts, not chat. The API contract is the single source of truth; frontend and backend build against the same spec. They diff in a pull request. Next month’s session reads them too.

Phase gates

Five phases from strategy to launch, with the API contract as a gate between design and implementation. Nothing moves forward without your approval, and no story is done until its acceptance criteria are verified. No skipped steps, no autonomous decisions on what ships; even autopilot stops short of main.

The three questions everyone asks

Too much process for a weekend project?

Then don’t run it. Archflow has two modes over the same schema, and new projects start in the light one.

quick

Solo, small, moving fast

One implicit release. Gates that record but never block. No ship ceremony until you ask for one. You still get agents, contracts, and phases, without the paperwork.

full

Team, releases, real stakes

Explicit release pipeline, enforced readiness gates, role lanes for PM, design, architecture, and QA. Everything a second contributor makes necessary.

Same schema either way, so switching costs nothing. When Archflow notices you’ve outgrown quick (a second release, a second contributor), it offers the upgrade. It never forces it.

Isn’t this just a big rules file?

That’s the right question, and for a while it was. Here’s what CLAUDE.md, AGENTS.md or .cursorrules can’t do.

A rules file describes the process. Archflow runs it.

A rules file tells the model how you’d like it to behave, then hopes it complies for the rest of the session. Archflow’s phases are state on disk: current-phase.yaml knows where you are, and the agent for that phase loads only that phase’s instructions.

Handoffs are files you can review, not chat you have to trust.

The API contract, roadmap and design system are artifacts in your repo. They diff in a pull request. A teammate can read them. Studio shows them as a board. Chat scrollback does none of that.

It reads what you already built, and keeps what it finds.

A rules file can tell the model to look around before each change. It cannot keep what it finds. /archflow:onboard reconstructs the plan around your codebase once, as a roadmap, releases, a contract and a history, and stores it in the repo.

Archflow is also made of files: plain markdown and YAML in .archflow/. If you want to fork the whole process and change every phase, that’s a text editor and a pull request. MIT.

How is this different from BMAD or gstack?

Less than either author would like. All three are MIT, and all three turn a coding agent into named specialists with gates between them.

Archflow makes one different bet: it reads the codebase you already have, once, up front, keeps what it finds in the repo as a roadmap, a release, a contract and a history, and shows you that plan on a board.

BMAD and gstack are bigger, older in the market, and better documented by third parties. If you have no code yet and want the most-travelled path, BMAD is a good choice. If you have a codebase, this is the one built for it. The honest version of each comparison, including where they win, is written up in full:

Detects the coding agents on your machine and sets Archflow up for each: Claude Code, OpenAI Codex, GitHub Copilot CLI, Cursor, Gemini CLI, OpenCode.
